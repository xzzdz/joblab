- [x] ตั้ง PostgreSQL ด้วย Docker (`docker-compose.yml`, port **5433**)
- [x] ติดตั้ง Prisma 7 + `@prisma/adapter-pg`
- [x] เขียน schema: `Company`, `Job` + enum `JobType` / `WorkMode` / `JobStatus`
- [x] migration แรก (`prisma/migrations/…_init`)
- [x] seed ข้อมูลตัวอย่าง 5 บริษัท 14 ประกาศ (เผยแพร่ 12, DRAFT 1, CLOSED 1)
- [x] Prisma Client singleton กัน connection รั่วตอน hot reload
- [x] หน้า `/jobs` รายการงาน + skeleton ตอนโหลด + empty state
- [x] หน้า `/jobs/[slug]` รายละเอียด + `generateMetadata` + 404
- [x] ตรวจ HTTP status ครบทุกเส้นทาง

### สิ่งที่ได้เรียนรู้ใน Phase นี้

1. **Server Component เรียก DB ได้ตรง ๆ** — ไม่ต้องมี API route, ไม่ต้อง `useEffect`, connection string ไม่หลุดไป browser
2. **`params` เป็น Promise แล้ว** — Next.js 15 ขึ้นไปต้อง `await props.params` ก่อนใช้
3. **Static vs ISR** — `npm run build` ตอนแรกขึ้น `○ Static` ที่ `/jobs` แปลว่าข้อมูลถูกอบไว้ตอน build
   ถ้า deploy ไปจะไม่เห็นประกาศใหม่เลย แก้ด้วย `export const revalidate = 60`
   👉 **อ่านผลลัพธ์ `npm run build` ทุกครั้ง** สัญลักษณ์ ○ / ƒ บอกพฤติกรรมจริงตอน production
4. **`loading.tsx` ครอบ route ลูกด้วย** — บั๊กจริงที่เจอใน Phase นี้:
   วาง `loading.tsx` ไว้ที่ `app/jobs/` ทำให้ `/jobs/[slug]` ถูกห่อ Suspense ไปด้วย
   Next เริ่ม stream ทันที → **ล็อก HTTP status ไว้ที่ 200** พอ `notFound()` ทำงานทีหลัง
   หน้าตาเป็น 404 แต่ status จริงคือ 200 → Google เก็บหน้า 404 เข้า index
   แก้โดยย้ายเข้า route group `app/jobs/(list)/` (ชื่อในวงเล็บไม่มีผลกับ URL)
5. **กรองสิทธิ์ที่ชั้น query** — `getPublishedJobBySlug` ใส่ `status: PUBLISHED` ไว้ใน where
   ทำให้เดา URL ประกาศ DRAFT ของบริษัทอื่นไม่ได้ (ทดสอบแล้ว ได้ 404 จริง)
6. **`Record<Enum, string>`** — ถ้าเพิ่มค่าใน enum แล้วลืมเพิ่มคำแปล TypeScript จะ error ตอน build

### สิ่งที่ได้เรียนรู้ใน Phase นี้

1. **ทำไมต้องมีด่าน 2 ชั้น** — `proxy.ts` เช็คจาก cookie เร็วแต่ไม่ปลอดภัยพอ เพราะถ้าเพิ่มหน้าใหม่
   แล้วลืมแก้ `matcher` หน้านั้นจะเปิดโล่งทันที ส่วน `requireUser()` ใน DAL อยู่ติดกับข้อมูล
   ลืมเรียกแล้วผลคือ "ไม่มีข้อมูลแสดง" ไม่ใช่ "ข้อมูลหลุด" — เอกสาร Next.js ก็ระบุชัดว่า
   proxy ไม่ควรเป็นด่านเดียว
2. **JWT session ไม่อัปเดตตาม DB** — ข้อมูลใน token คือภาพ ณ ตอนล็อกอิน ถ้าเปลี่ยน role ของใครใน DB
   token เดิมยังถือ role เก่าจนหมดอายุ เลยต้องอ่าน role จาก DB ซ้ำใน `requireRole()`
3. **ตอบ error ให้เหมือนกันหมด** — ล็อกอินพลาดตอบว่า "อีเมลหรือรหัสผ่านไม่ถูกต้อง" เสมอ
   ไม่แยกว่าผิดตรงไหน เพราะการแยกคือการยืนยันให้คนโจมตีรู้ว่าอีเมลไหนมีบัญชีอยู่จริง
4. **timing attack** — ถ้าไม่เจอผู้ใช้แล้ว return ทันที จะเร็วกว่ากรณีเจอราว 20 เท่า
   คนโจมตีจับเวลาก็รู้ได้ว่าอีเมลไหนมีอยู่ เลยต้องเทียบกับแฮชหลอกให้เสียเวลาพอ ๆ กัน
5. **race condition ตอนสมัคร** — เช็คอีเมลซ้ำด้วย `findUnique` ก่อน `create` ปิดช่องไม่ได้จริง
   เพราะอาจมี request แทรกระหว่างนั้น ต้องให้ unique constraint ของ DB เป็นคนตัดสิน แล้วดักโค้ด `P2002`
6. **การอ่าน cookie ทำให้ทั้ง route กลายเป็น dynamic** — พอใส่ header ที่รู้จักผู้ใช้ใน root layout
   `/jobs` เปลี่ยนจาก `○ Static` เป็น `ƒ Dynamic` ทันที `revalidate = 60` เลยไม่มีผลอีกต่อไป
   (บันทึกไว้ในโค้ดแล้ว วิธีแก้อยู่ใน Backlog)
7. **`declare module` ต้องชี้ให้ถูกโมดูล** — เขียน `declare module "next-auth/jwt"` แล้วไม่มีผล
   เพราะไฟล์นั้นเป็นแค่ `export * from "@auth/core/jwt"` ต้อง augment ที่ต้นทาง

- [x] **ownership อยู่ใน `where` ของทุก query และทุกคำสั่งเขียน**

- [x] ห้ามลบประกาศที่กำลังเผยแพร่ ต้องปิดรับก่อน

- [x] slug สร้างอัตโนมัติจากชื่อตำแหน่ง รองรับภาษาไทย และกันซ้ำ

### สิ่งที่ได้เรียนรู้ใน Phase นี้

1. **เอาเงื่อนไขความเป็นเจ้าของไปไว้ใน `where` อย่าเขียนเป็น `if` ทีหลัง**
   ```ts
   // ❌ ปลอดภัยตราบใดที่ยังจำได้ว่าต้องเขียน if
   const job = await prisma.job.findUnique({ where: { id } });
   if (job.company.ownerId !== user.id) throw ...

   // ✅ ลืมไม่ได้ เพราะไม่มีทางดึงข้อมูลออกมาโดยไม่ผ่านเงื่อนไข
   prisma.job.findFirst({ where: { id, company: { ownerId: user.id } } })
   ```
   ผลต่างคือ "ลืมแล้วหาไม่เจอ" (ปลอดภัย) กับ "ลืมแล้วแก้ข้อมูลคนอื่นได้" (ข้อมูลรั่ว)
2. **`updateMany` / `deleteMany` ปลอดภัยกว่า `update` / `delete` ในบริบทนี้**
   เพราะ `update` รับ `where` ได้เฉพาะฟิลด์ unique จึงแนบเงื่อนไขเจ้าของไปด้วยไม่ได้
   ส่วน `updateMany` แนบได้ → ถ้าสิทธิ์ไม่ผ่านจะอัปเดต 0 แถวแทนที่จะเขียนทับข้อมูลคนอื่น
3. **ข้อมูลที่ตัดสินเรื่องสิทธิ์ต้องมาจาก session ไม่ใช่จากฟอร์ม**
   `companyId` ตอนสร้างประกาศดึงจาก `ownerId` ของผู้ใช้ ไม่ได้รับมาจาก input
4. **Server Action = endpoint สาธารณะ** ยิงตรงได้โดยไม่ผ่านหน้าเว็บเลย
   การซ่อนปุ่มหรือกันที่ layout จึงไม่ใช่ความปลอดภัย ทุก action ต้องเช็คสิทธิ์เองทุกตัว
5. **แยกการแก้เนื้อหาออกจากการเปลี่ยนสถานะ** ตอนแรกออกแบบให้ฟอร์มแก้ไขมีช่องสถานะด้วย
   แล้วพบว่าเปิดประกาศที่ปิดรับแล้วมาแก้คำผิด ประกาศจะกลับมาเปิดรับเองโดยไม่มีใครสั่ง
6. **สถานะควรเป็น state machine ไม่ใช่ค่าอะไรก็ได้** กำหนดชัดว่าเปลี่ยนจากไหนไปไหนได้บ้าง
   ทำให้ `PUBLISHED → DRAFT` (ประกาศหายเงียบ ๆ + วันเผยแพร่หาย) เกิดขึ้นไม่ได้เลย

### ⚠️ เปลี่ยนจากแผนเดิม: ใช้ offset ไม่ใช่ cursor

แผนเดิมเขียนไว้ว่าจะทำ cursor pagination แต่เปลี่ยนเป็น offset (`skip`/`take`) เพราะ
หน้านี้ต้องบอกได้ว่า "หน้า 2 จาก 5" และกระโดดข้ามหน้าได้ ซึ่ง cursor ทำไม่ได้
(cursor รู้แค่ "ถัดจากรายการนี้" ไม่รู้ว่าตัวเองอยู่หน้าที่เท่าไร)

cursor เหมาะกับ feed ที่เลื่อนลงเรื่อย ๆ หรือ API — ย้ายไปอยู่ใน Backlog แล้ว

### ผลการวัด (ข้อมูล 50,000 แถว, EXPLAIN ANALYZE)

| query | ก่อนใส่ index | หลังใส่ index | วิธีอ่านข้อมูล |
|---|---|---|---|
| หน้าแรก ไม่กรอง | 0.075 ms | — | Index Scan (index เดิมพอแล้ว) |
| กรอง type + workMode | 0.069 ms | — | Index Scan (index เดิมพอแล้ว) |
| ค้นหาแล้ว**เจอเยอะ** | 0.124 ms | — | Index Scan |
| ค้นหาแล้ว**ไม่เจอเลย** | **26.6 ms** | **0.59 ms** | Seq Scan → Bitmap Heap Scan |
| นับจำนวนผลค้นหาที่ไม่เจอ | **24.9 ms** | **0.045 ms** | Seq Scan → Bitmap Heap Scan |
| หน้า 1000 (OFFSET 6000) | 1.7 ms | — | Index Scan |
| หน้า 5000 (OFFSET 30000) | 14.3 ms | 14.3 ms | Seq Scan (index ช่วยไม่ได้) |

### สิ่งที่ได้เรียนรู้ใน Phase นี้

1. **ต้องวัดกรณีที่แย่ที่สุด ไม่ใช่กรณีที่ใช้บ่อย** — ค้นคำที่เจอเยอะใช้เวลา 0.1 ms
   แต่ค้นคำที่ไม่เจอเลยใช้ 26 ms ต่างกัน 200 เท่า เพราะตอนเจอเยอะ Postgres
   เจอครบ 6 รายการแล้วหยุด แต่ตอนไม่เจอมันต้องอ่านจนหมดตารางถึงจะรู้ว่าไม่มี
2. **`ILIKE '%คำ%'` ใช้ index ธรรมดาไม่ได้** เพราะ B-tree เรียงตามตัวอักษรตัวแรก
   ต้องใช้ GIN + `gin_trgm_ops` ที่หั่นข้อความเป็นชุดละ 3 ตัวอักษรแล้ว index จากชิ้นส่วน
3. **บางอย่าง Prisma เขียนใน schema ให้ไม่ได้** — `CREATE EXTENSION pg_trgm` ต้องเติมมือ
   ในไฟล์ migration ส่วนตัว index ประกาศใน schema ได้ด้วย `@@index([title(ops: raw(...))], type: Gin)`
4. **OFFSET ลึก ๆ ไม่มี index ไหนช่วยได้** เพราะ Postgres ต้องไล่อ่านแล้วทิ้งของก่อนหน้าทั้งหมด
   ทางแก้คือ **จำกัดเลขหน้าสูงสุด** (เราตั้งไว้ 1000 → 14 ms เหลือ 1.7 ms) หรือเปลี่ยนไปใช้ cursor
5. **URL คือ input จากผู้ใช้** ต้อง validate เหมือนฟอร์ม `?page=99999999` หรือ `?type=DROP_TABLE`
   ต้องไม่ทำให้หน้าพังและไม่ทำให้ query เพี้ยน
6. **`OR` ซ้อนกันสองที่ในเงื่อนไขเดียวจะทับกันเงียบ ๆ** เพราะ object ใน JavaScript มี key ซ้ำไม่ได้
   ต้องรวมใส่ array `AND` แทน
7. **`<form method="get">` ธรรมดาให้ของฟรีเยอะกว่าที่คิด** — ตัวกรองอยู่ใน URL, back/forward ใช้ได้,
   bookmark ได้, search engine เก็บ index ได้ และทำงานได้แม้ JavaScript พัง โดยไม่ต้องเขียน state สักบรรทัด

### สิ่งที่ได้เรียนรู้ใน Phase นี้

1. **ตรวจไฟล์ต้องดูที่ไบต์จริง ไม่ใช่นามสกุล** — เปลี่ยนนามสกุล `.exe` เป็น `.pdf` ใช้เวลา 2 วินาที
   ส่วน MIME type ที่เบราว์เซอร์ส่งมาก็ปลอมได้ ด่านที่กันได้จริงคือเทียบ 5 ไบต์แรกกับ `%PDF-`
   (ทดสอบแล้ว: ส่งไฟล์ที่ขึ้นต้นด้วย `MZ` ในชื่อ `resume.pdf` → ถูกปฏิเสธ)
2. **ไฟล์ของผู้ใช้ห้ามอยู่ใน `public/`** — เพราะโฟลเดอร์นั้นเปิดให้ทุกคนโหลดโดยไม่ต้องล็อกอิน
   resume มีเบอร์โทรและที่อยู่ ต้องผ่าน route ที่ตรวจสิทธิ์เสมอ
3. **ห้ามเอาชื่อไฟล์จากผู้ใช้ไปต่อ path** — ชื่อว่า `../../.env` จะทำให้เขียนทับไฟล์นอกโฟลเดอร์ได้
   (path traversal) เราจึงสุ่ม UUID เป็นชื่อบนดิสก์ แล้วเก็บชื่อเดิมไว้แค่ไว้แสดงผล
4. **เขียนไฟล์สำเร็จแต่บันทึก DB ไม่สำเร็จ = ไฟล์ขยะ** ต้องลบไฟล์ทิ้งใน `catch` เสมอ
   ไม่งั้นดิสก์จะสะสมไฟล์ที่ไม่มีใครอ้างถึงไปเรื่อย ๆ
5. **`useOptimistic` เขียน rollback เองไม่ได้และไม่ต้องเขียน** — ถ้า action ล้มเหลว
   React ย้อนสถานะกลับให้เองเมื่อ transition จบ ต่างจากการ `setState` เองที่ต้องจัดการ rollback
6. **Next จำกัด body ของ Server Action ไว้ 1 MB** ไฟล์ที่ใหญ่กว่านั้นไม่เคยมาถึงโค้ดเรา
   ผู้ใช้เลยเห็น error ดิบแทนข้อความที่เราเขียน → ต้องตั้ง `serverActions.bodySizeLimit`
   ให้สูงกว่าขนาดที่เรารับจริง ไม่งั้นป้าย "ไม่เกิน 2 MB" บนฟอร์มจะเป็นคำโกหก
7. **`groupBy` ครั้งเดียวดีกว่านับทีละแถว** — หน้ารายการประกาศถ้าให้แต่ละแถวไปนับใบสมัครเอง
   จะยิง query เท่ากับจำนวนแถว + 1 (ปัญหา N+1)

### 14 ส.ค. 2569 — Phase 5 + คู่มือ

ทำระบบสมัครงานครบวงจร และเขียน [GUIDE.md](GUIDE.md) สำหรับคนที่เพิ่งเข้ามาอ่านโปรเจค

ตัดสินใจอะไรไปบ้าง:
- **เก็บ resume ลงดิสก์เองก่อน ไม่ใช้ service สำเร็จรูป** — จะได้เข้าใจว่าการรับไฟล์
  ต้องตรวจอะไรบ้าง แล้วซ่อนไว้หลัง `storage.ts` เพื่อให้วันย้ายไป S3 แก้แค่ไฟล์เดียว
- **resume ผูกกับใบสมัคร ไม่ใช่ผูกกับโปรไฟล์** — คนจริง ๆ ส่ง resume คนละเวอร์ชันตามตำแหน่งที่สมัคร
- **URL ดาวน์โหลดอ้างถึง "ใบสมัคร" ไม่ใช่ "ไฟล์"** เพราะสิทธิ์ผูกกับใบสมัคร
- **`WITHDRAWN` ไม่อยู่ในรายการที่บริษัทตั้งได้** — ถ้าบริษัทตั้งได้ ประวัติจะโกหกว่า
  ผู้สมัครถอนเองทั้งที่ถูกปฏิเสธ
- **บริษัทดึงใบที่ถูกถอนกลับมาไม่ได้** — การตัดสินใจนั้นเป็นของผู้สมัคร

บั๊กที่เจอและแก้:
- ไฟล์ใหญ่กว่า 1 MB ไม่เคยมาถึงโค้ดตรวจของเราเลย เพราะ Next จำกัด body ของ Server Action
  ไว้ที่ 1 MB ผู้ใช้เห็น `Body exceeded 1 MB limit` แทนข้อความ "ไฟล์ใหญ่เกิน 2 MB"
  → ตั้ง `serverActions.bodySizeLimit: "3mb"` ใน `next.config.ts` + เพิ่มการเช็คฝั่ง client
  (แก้ config แล้วต้องรีสตาร์ต dev server ด้วย ไม่งั้นไม่มีผล)

เสียเวลาเปล่าไปกับ:
- ทดสอบไฟล์ 3 MB กับเพดาน 3 MB แล้วงงว่าทำไมยังไม่ผ่าน — ลืมนับ overhead ของ multipart
  เปลี่ยนไฟล์ทดสอบเป็น 2.5 MB ก็ผ่านทันที **ตั้งค่าทดสอบให้อยู่กลางช่วงเสมอ ไม่ใช่ขอบพอดี**
- พยายาม replay action ของบอร์ด Kanban ผ่าน HTTP แต่มันถูกเรียกจากฝั่ง client
  รูปแบบเข้ารหัสเป็นของภายใน React → เปลี่ยนไปทดสอบเงื่อนไข `where` ที่เป็นด่านจริงแทน
  และทดสอบ action ที่อยู่ใน `<form>` จริง (ถอนใบสมัคร) ผ่าน HTTP เต็มรูปแบบ

ตรวจสอบแล้ว — ทดสอบการโจมตี 32 ข้อ ผ่านทั้งหมด:

- **หน้าบอร์ด (4 ข้อ):** เจ้าของ 200 · **บริษัทอื่นเดา id ถูกก็ได้ 404** · ผู้สมัคร 307 · ไม่ล็อกอิน 307
- **สิทธิ์แก้ข้อมูล (5 ข้อ):** ผู้สมัครถอนใบของคนอื่นไม่ได้ (replay ฟอร์มจริงผ่าน HTTP) ·

### 14 ส.ค. 2569 — Phase 4

ทำค้นหา/กรอง/แบ่งหน้า แล้วปรับ index จากการวัดผลจริง

ตัดสินใจอะไรไปบ้าง:
- **เปลี่ยนจาก cursor เป็น offset** (เหตุผลอยู่ในหัวข้อ Phase 4 ข้างบน)
- **จำกัดเลขหน้าสูงสุดไว้ที่ 1000** เพื่อกันคนยิง `?page=99999999` แล้วทำ DB ทำงานหนักฟรี ๆ
- **ตัวกรองที่ผู้ใช้ส่งค่าผิดมา ให้เงียบ ๆ แล้วแสดงผลปกติ** ไม่ขึ้น error
  เพราะ URL เพี้ยนมักเกิดจากลิงก์เก่าหรือ copy มาไม่ครบ ไม่ใช่ความผิดของคนกด
- **ประกาศที่ไม่ระบุเงินเดือนจะไม่ถูกแสดงเมื่อผู้ใช้กรองเงินเดือน** เพราะรับประกันไม่ได้ว่าถึงเกณฑ์
- **dropdown สถานที่สร้างจากข้อมูลจริงด้วย `groupBy`** จะได้ไม่มีตัวเลือกที่กดแล้วผลลัพธ์ว่าง
- **ลบ `export const revalidate = 60` ออกจาก `/jobs`** เพราะหน้านี้อ่าน `searchParams` แล้ว
  จึงเป็น dynamic ถาวร การเก็บบรรทัดที่ไม่มีผลไว้มีแต่ทำให้คนอ่านโค้ดเข้าใจผิด

การทดลองเรื่อง index (ทำแล้วลบข้อมูลทดลองทิ้ง):
- สร้างประกาศปลอม 50,000 แถว แล้ววัดด้วย `EXPLAIN ANALYZE` เพราะข้อมูล 14 แถวไม่มีทางเห็นความต่าง
- พบว่า index เดิม `(status, publishedAt)` รับมือได้ดีเกือบทุกกรณีอยู่แล้ว
- จุดที่พังคือ **ค้นหาแล้วไม่เจอ**: 26.6 ms และ COUNT อีก 24.9 ms → รวมเกือบ 52 ms ต่อ 1 การค้นหา
- แก้ด้วย GIN + `gin_trgm_ops` → เหลือ 0.59 ms และ 0.045 ms
- ลบข้อมูลทดลองออกโดยตรวจจำนวนก่อนลบตามกฎข้อ 4 (จะลบ 50,000 · เหลือ 14) แล้ว `VACUUM ANALYZE`

เสียเวลาเปล่าไปกับ:
- สคริปต์ทดสอบอ่าน `href` จาก HTML แล้วเอาไปยิงต่อโดยลืมแปลง `&amp;` กลับเป็น `&`
  ทำให้พารามิเตอร์กลายเป็น `amp;page` → หน้า 2 แสดงผลเหมือนหน้า 1 แล้วผมนึกว่าโค้ดผิด
  **อีกครั้งที่เครื่องมือทดสอบผิด ไม่ใช่แอปผิด**

ตรวจสอบแล้ว (ยิง HTTP จริงทั้งหมด):
- ตัวกรองเดี่ยว 9 แบบ และตัวกรองผสม 3 แบบ ได้จำนวนตรงกับข้อมูลจริงทุกอัน
- แบ่งหน้า: 12 รายการ = หน้า 1 (6) + หน้า 2 (6) ไม่มีรายการซ้ำหรือหาย
- กรอง `type=FULL_TIME` (9 รายการ): หน้า 1 ได้ 6 · หน้า 2 ได้ 3 และลิงก์พาตัวกรองติดไปด้วย
- chip ทั้ง 3 อันลบตัวเองออกและเก็บตัวกรองที่เหลือไว้ถูกต้อง
- ค่ามั่วจาก URL: `type=DROP_TABLE`, `salary=abc`, `page=-5`, `page=99999`, พารามิเตอร์ซ้ำ,
  พารามิเตอร์ที่ไม่รู้จัก → ไม่พังสักอัน และไม่ทำให้ผลลัพธ์เพี้ยน

  ตอนซ้ำจะเติมเลขต่อท้าย (`-2`, `-3`) และมี unique constraint ของ DB เป็นด่านสุดท้าย
- **ไม่เปลี่ยน slug ของบริษัทตอนเปลี่ยนชื่อบริษัท** เพราะ slug อยู่ใน URL ที่คนอาจแชร์ไว้แล้ว
- **ปุ่มเปลี่ยนสถานะใช้ `<form action={serverAction}>` ตรง ๆ** ไม่ทำเป็น Client Component
  ทั้งหน้ารายการมีแค่ปุ่มยืนยันการลบเท่านั้นที่ส่ง JavaScript ไปฝั่ง browser

บั๊กที่เจอและแก้ (**บั๊กจริงที่ผู้ใช้ไทยจะเจอแน่นอน**):
- ประกาศที่ชื่อเป็นภาษาไทยขึ้นบนหน้ารายการได้ แต่กดเข้าไปดูแล้ว **404**
  สาเหตุ: `params.slug` ใน Page มาถึงแบบ **ยังไม่ถูก decode** (`%E0%B8%99...`)
  เอาไปค้น DB ตรง ๆ จึงไม่เจอ ทั้งที่ข้อมูลมีอยู่
  แก้ด้วย `decodeRouteParam()` ใน `src/lib/route-params.ts`
  จุดที่หลอกให้หลงทาง: Route Handler (`route.ts`) ได้ค่าที่ decode มาแล้ว — **สองที่ทำงานไม่เหมือนกัน**
  และ slug ภาษาอังกฤษไม่มีอาการเลย บั๊กนี้จึงซ่อนอยู่จนกว่าจะมีข้อมูลไทยเข้ามา

เสียเวลาเปล่าไปกับ:
- ตัวอักษรไทยที่ส่งผ่าน `curl -F` กลายเป็น `?????` ในฐานข้อมูล ตอนแรกนึกว่าแอปพัง
  ที่จริงคือ **Git Bash บน Windows แปลง UTF-8 ใน command-line argument เสีย**
  พอส่งค่าจากไฟล์แทน (`-F 'title=<file.txt'`) ข้อมูลไทยเข้าฐานข้อมูลถูกต้องทุกตัว
  บันทึกวิธีเลี่ยงไว้ใน CLAUDE.md แล้ว

ตรวจสอบแล้ว — จำลองการโจมตีจริงด้วยการยิง Server Action ตรงข้าม UI:
- บริษัท A เรียก `updateJob` ทับประกาศบริษัท B → ตอบ "ไม่พบประกาศนี้", DB ไม่เปลี่ยนสักฟิลด์
- บริษัท A เรียก `setJobStatus` ปิดรับประกาศบริษัท B → ไม่มีผล
- บริษัท A เรียก `deleteJob` ลบประกาศบริษัท C → ประกาศยังอยู่
- ผู้สมัครงานเรียก `deleteJob` ตรง ๆ → เด้งออกที่ `requireRole`
- ตรวจฐานข้อมูลหลังโจมตีทั้งหมด: ทุกฟิลด์คงเดิม จำนวนประกาศเท่าเดิม
- flow ปกติ: สร้างฉบับร่าง → ไม่โผล่หน้าสาธารณะ → เผยแพร่ → โผล่ (12→13) →
  ลบตอนเผยแพร่ไม่ได้ → `PUBLISHED → DRAFT` ทำไม่ได้ → ปิดรับ → หายจากหน้าสาธารณะ (13→12) → ลบได้
- validation: รายละเอียดสั้นเกิน / เงินเดือนสูงสุด < ต่ำสุด → ไม่บันทึกและขึ้น error ถูกช่อง
- `lint` / `typecheck` / `build` ผ่าน, ข้อมูลกลับสู่สภาพหลัง seed พอดี (6 ผู้ใช้ · 5 บริษัท · 14 ประกาศ)

### 14 ส.ค. 2569 — Phase 2

ทำระบบสมาชิกจนล็อกอินได้จริง

ตัดสินใจอะไรไปบ้าง:
- **JWT session ไม่ใช่ database session** — ไม่ได้เลือกเอง แต่ Auth.js รองรับ Credentials
  ได้เฉพาะ strategy นี้ ผลข้างเคียงคือต้องอ่าน role จาก DB ซ้ำใน DAL
- **`Company.ownerId` เป็น optional ก่อน** — เพื่อให้ migration ไม่ทำข้อมูล seed เดิมพัง
  แล้ว backfill ผ่าน seed (วิธีเดียวกับที่ต้องทำบน production)
- **ยังไม่ทำ OAuth** — จะได้ไม่ต้องเพิ่มตาราง Account/Session ตอนนี้ ย้ายไป Backlog
- **สร้าง migration ด้วย `migrate diff` + `migrate deploy`** เพราะ `migrate dev` เป็นคำสั่ง
  แบบโต้ตอบที่รันใน terminal ของ agent ไม่ได้ (วิธีบันทึกไว้ใน CLAUDE.md แล้ว)

บั๊กที่เจอและแก้:
- `declare module "next-auth/jwt"` ไม่มีผล ทำให้ `token.id` เป็น `unknown` → ต้อง augment
  `@auth/core/jwt` แทน เพราะ next-auth/jwt เป็นแค่ re-export
- `token.id = user.id` typecheck ไม่ผ่านเพราะ Auth.js ประกาศ `User.id` เป็น optional → เพิ่ม guard
- dev server ตัวเก่ายังค้างอยู่ใน background หลัง Phase 1 และมันถูกสตาร์ตก่อนที่ `.env`
  จะมี `AUTH_SECRET` ทำให้ `/api/auth/csrf` ตอบผิด → ต้อง kill process แล้วเริ่มใหม่

อุบัติเหตุ (บันทึกไว้เตือนความจำ):
- ตอนลบผู้ใช้ทดสอบใช้เงื่อนไข `email contains "example.com"` ซึ่งไปแมตช์อีเมลเจ้าของบริษัท
  ใน seed ด้วย พอ `onDelete: Cascade` ทำงาน บริษัทกับประกาศงานหายไป 4 ชุด
  กู้คืนด้วย `npm run db:seed` ได้ครบเพราะ seed เขียนแบบ idempotent
  → เพิ่มกฎใน CLAUDE.md แล้ว: ก่อน `deleteMany` ต้อง `count` ด้วยเงื่อนไขเดียวกันดูก่อนเสมอ

ตรวจสอบแล้ว (ยิง HTTP จริงทั้งหมด):
- `/account` ไม่ล็อกอิน → 307 ไป `/login?callbackUrl=%2Faccount`; ล็อกอินแล้ว → 200
- ล็อกอินรหัสผิด → ไม่ได้ session cookie, redirect กลับพร้อม `error=CredentialsSignin`
- ล็อกอินถูก → ได้ cookie ที่เป็น `HttpOnly` + `SameSite=Lax` และ token ถูกเข้ารหัส (JWE)
- `/login` ตอนล็อกอินอยู่ → 307 ไป `/jobs`
- สมัครสมาชิกใหม่ → 303 ไป `/jobs` พร้อม session; อีเมลซ้ำ / รหัสไม่ตรงกัน / รหัสสั้นเกิน → ขึ้น error ถูกต้อง
- ข้อมูลใน DB: อีเมลถูกแปลงเป็นตัวพิมพ์เล็ก, เก็บเฉพาะ bcrypt hash ไม่มี plain text
- `lint` / `typecheck` / `build` ผ่าน
